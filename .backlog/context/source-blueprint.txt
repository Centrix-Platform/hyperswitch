Architectural recommendation
Build a platform-owned API and domain layer around Hyperswitch, while retaining Hyperswitch as the
payment execution engine. This gives you a controlled B2B2B model now and a practical path to Kotlin later.
Your proposed entity mapping is workable, with two qualifications: a BusinessProfile needs a separate merchant
lifecycle and isolation model, and terminal identity/configuration must be modeled separately from connector
credentials.
This blueprint is grounded in the local core checkout, commit c5ecb434b419d2c473cf2882a3866de9146abdec, and
the upstream dashboard and Android repositories inspected for the architectural review. The core currently defaults
to the v1 feature set; pin compatible versions across all forks before implementation.

platform authentication and connected-merchant handling; that is an alternative topology, not another name for
infrastructure tenancy. See the platform authentication implementation.

3. Aggregator Portal and access control
Make the Aggregator Portal an authenticated, tenant-scoped product. The upstream Control Center uses React
and ReScript, with some TypeScript. Its configuration already exposes branding and endpoint settings, so start by
adapting those surfaces. See the dashboard package configuration and runtime configuration.
Frontend changes should include:
 Aggregator branding resolved from a verified custom-domain mapping.
 Merchant onboarding and approval status.
 Terminal inventory, enrollment, assignment, suspension and processing bindings.
 Aggregator-owned acquirer connections and merchant-specific processing configuration.
 Payment, refund, dispute and reconciliation views scoped to the permitted merchant set.
 Operational-key and webhook management.
 Team invitations and scoped role management.
Treat branding as validated data: colors, approved logos, display names and support links. Avoid tenant-supplied
executable JavaScript. Namespace frontend caches by environment and aggregator, and clear sensitive state on
logout or context changes.
For browser authentication, use OIDC with a portal backend-for-frontend. Prefer secure, HttpOnly cookies with CSRF
protection. API keys belong in aggregator servers, not browser storage.
On login:
1. Authenticate the user.
2. Load their active aggregator membership.
3. Resolve the corresponding organization and MerchantAccount.
4. Issue a session bound to that aggregator and environment.
5. Derive permissions and any permitted merchant subset from server-controlled membership data.
A suitable trusted context is:
JSON
{
  "subject": "user_123",
  "platform_id": "platform_live",
  "aggregator_id": "agg_A",
  "environment": "live",
  "permissions": ["merchants:create", "terminals:link", "payments:read"],
  "merchant_scope": "all",
  "authorization_version": 12
}
If users legitimately belong to several aggregators, switching context should produce a newly authorized session. A
dropdown or request header must not independently change authority.

4. PostgreSQL tenancy and pooled connections
Enforce tenancy inside each database transaction, not only when borrowing a pooled connection. For every
tenant-scoped unit of work:
SQL
BEGIN;
-- $1 comes from authenticated server context.
SELECT set_config('app.aggregator_id', $1, true);
-- Parameterized application queries run here.
COMMIT;
The final true makes the setting transaction-local. This avoids retaining one aggregator's context on a pooled
connection after commit or rollback. PostgreSQL documents the corresponding lifetime in its SET reference.

Implement a required storage entry point:

It should:
 Reject missing tenant context.
 Acquire a connection and begin a transaction.
 Set trusted context before any tenant-scoped query.

 Commit or roll back before releasing the connection.
Use PostgreSQL RLS as defense in depth, with both USING and WITH CHECK. Runtime roles must be non-owner roles
without BYPASSRLS; use FORCE ROW LEVEL SECURITY where applicable. PostgreSQL explains owner and superuser
exceptions in its row security documentation.
Additional requirements:
 Include aggregator_id in indexes used by tenant-scoped queries and in relevant uniqueness constraints.
 Use composite foreign keys to prevent cross-aggregator relationships.
 Scope the native Hyperswitch tables too. Policies on your new registry do not protect native payments, refunds
or customers.
 For native tables, enforce the resolved Hyperswitch MerchantAccount boundary; add explicit merchant/profile
ownership where your public model needs it.
 Where denormalized tenant columns are added, backfill and validate their consistency before making them
mandatory.
 Test accounts pools, payment pools, workers, replica reads and failed transactions.
 Namespace Redis entries, queues, exports, analytics filters and object-storage paths.
RLS based on a session setting protects against missing predicates. It does not independently protect against a fully
compromised application that can set arbitrary context. Customers should never have database access. Stronger
isolation can use separate database roles, databases or deployment cells.
The checkout supports both PostgresOnly and RedisKv payment storage paths. For the first production release,
prefer authoritative PostgreSQL persistence for critical payment admission and state. RLS cannot protect records
served exclusively from Redis; any KV path and drainer must receive equivalent isolation treatment. See the payment
storage implementation.

5. Terminal identity and transaction routing
Authenticate the terminal before considering its routing fields. A submitted terminal_id, serial number or TID is
a claim, not proof of identity.
Enrollment should establish:
CONTRACT / FLOW
aggregator
  └─ merchant
      └─ logical terminal deployment
          ├─ device public key / certificate
          ├─ approved APK package and signing identity
          ├─ terminal model and vendor payment application
          ├─ firmware / kernel / application versions
          ├─ activation and revocation state
          └─ permitted processing bindings
A processing binding should identify:
CONTRACT / FLOW
merchant + terminal deployment
  → acquirer account
  → profile-specific MCA projection
  → acquirer MID / TID
  → certification bundle
  → encryption/key domain
  → supported currencies and transaction types
  → binding/configuration version
On a charge:
1. Authenticate the SDK session and device proof.
2. Resolve aggregator, merchant and terminal from trusted server records.
3. Check all three are active and mutually related.
4. Validate amount, currency, operation, freshness and signed request fields.
5. Load eligible terminal bindings.
6. Intersect those bindings with aggregator routing policy.
7. Freeze the selected route, configuration and credential version on the attempt.
8. Execute through Hyperswitch or a dedicated terminal protocol adapter.
The SDK must not choose an arbitrary MCA, acquirer URL, credential reference or tenant header.
For terminal traffic, eligible routes are constrained by the certified integration and encryption domain. Ciphertext
prepared for Acquirer A generally cannot be forwarded to Acquirer B. A fallback may require a new terminal
interaction.
"Pre-certified terminal" also needs precise meaning. Hardware or kernel approval does not establish that a new
gateway-to-acquirer integration is approved. EMVCo describes Level 3 testing as validation of the terminal's
integration with its acceptance infrastructure. Track the approved combination and its change-control requirements.
See EMV Level 3 testing.

6. Distributed idempotency and payment safety
Use Redis for coordination and PostgreSQL for durable idempotency. A production payment design cannot
safely promise duplicate prevention using Redis locks alone. Redis documents how asynchronous replication and
failover can allow two clients to believe they own a lock. See Redis distributed lock guidance.
Use three layers:
Layer
Purpose
Redis
Coalesce concurrent requests, cache safe responses, enforce limits
PostgreSQL
Uniquely reserve operations and persist authoritative workflow state
Acquirer integration
Apply documented downstream duplicate controls and resolve ambiguous outcomes
Define the durable idempotency scope as:
CONTRACT / FLOW
environment + aggregator_id + merchant_id
+ operation_scope + idempotency_key
operation_scope distinguishes charge creation from capture, refund and reversal, including the target resource
where appropriate. Do not include the calling operational key in the scope: rotating credentials must not permit the
same operation again.
A safe algorithm is:
1. Authenticate and authorize first.
2. Compute a canonical request fingerprint covering immutable business fields and the stable payment-payload
reference.
3. Attempt a short Redis lease using SET ... NX PX, with a random ownership value.
4. In a short PostgreSQL transaction, insert the operation using its unique idempotency constraint.
5. On conflict, load the existing operation. Same fingerprint and completed: return the stored safe result. Same
fingerprint and running or uncertain: return its operation reference. Different fingerprint: return 409
idempotency_conflict.
6. Commit the operation and dispatch reference before initiating the external financial action.
7. Claim the attempt using a conditional state transition.
8. Execute outside the database transaction.
9. Persist the result and an outbox event in a new short transaction.
10. Update the Redis response cache as an optimization.

A useful state model is:
CONTRACT / FLOW
ADMITTED → DISPATCHING → SUCCEEDED
                      → FAILED
                      → UNKNOWN → inquiry / callback / reconciliation
UNKNOWN means that a financial outcome may exist. It must not be treated as a failed charge.
Operational rules:
 Release or renew Redis leases using atomic ownership checks.
 Do not authorize a new charge merely because a lease expired.
 Use durable versions/fencing to reject stale database updates.
 Recognize that a database fence cannot stop an already-running external request.
 Reuse the original downstream transaction reference only according to the acquirer's documented duplicate
semantics.
 A unique reference field alone is not proof that the acquirer deduplicates.
 If the worker crashes around dispatch, conservatively reconcile the original attempt before retrying.
 After an ambiguous timeout, do not automatically route to another acquirer.
 Deduplicate inbound acquirer notifications and enforce valid state transitions.
 Preserve durable duplicate protection beyond Redis TTL expiry.
 Define how SDK retries reuse the same encrypted request or stable payload reference; fresh randomized
ciphertext must not accidentally redefine the operation.
Keep sensitive authentication payloads out of normal outbox records and replay caches. Dispatch events should
contain secure references, not raw card/PIN data.
This design reduces contention through short transactions and indexed conditional writes. It cannot guarantee that
database deadlocks never occur. Use consistent lock ordering, bounded lock waits and retries for safely repeatable
database transactions; never repeat a financial side effect as part of a generic transaction retry.
Hyperswitch already has Redis-based API locking. Extend and integrate its behavior instead of assuming it is a
complete durable idempotency contract. See the existing locking implementation.
For geographic resilience, give each aggregator or payment a home region and one authoritative writer. Start with
controlled failover, not independent active writers sharing only eventually replicated idempotency data.

Card/PIN
  → approved terminal secure component
  → vendor/acquirer-approved encryption
  → opaque encrypted result or token
  → gateway forwarding
  → authorized decryption endpoint
Do not design your general SDK to read clear PAN, track data or PIN blocks and then apply custom RSA encryption.
Where an approved integration requires application-layer public-key encryption:
 Use a vetted envelope format such as JWE and an explicitly allowed algorithm suite.
 Fetch recipient keys from authenticated, versioned configuration.
 Validate kid, key purpose, environment and expiry.
 Bind amount, currency, merchant, terminal, operation and session to the authenticated envelope.
 Keep private decryption keys outside the APK and general gateway.
 Retain TLS; message encryption does not authenticate the transport endpoint.
JWE defines the envelope structure, not a PCI approval or terminal key-management system. Terminal PIN/data
encryption and HSM key management must follow the selected approved solution. See RFC 7516.
PCI SSC states that PTS-approved terminals alone do not guarantee scope reduction; validated P2PE solutions can
facilitate it. If your gateway decrypts payment data, plan for the corresponding cardholder-data environment. Confirm
the actual service-provider boundary against the deployed solution. See PCI terminal assessment guidance.
For ordinary Android phones accepting NFC or PIN, use an appropriate validated mobile acceptance solution rather
than treating the checkout SDK as a SoftPOS stack. See PCI MPoC.

APK communication and recovery
Use local calls for an embedded SDK and secured IPC only where another app is involved.
 Inside the aggregator APK, prefer Kotlin APIs/coroutines and lifecycle-aware callbacks.
 Keep internal services non-exported.
 For another payment app, use an explicit component and the vendor's documented service/Activity Result
contract.
 For exported Binder/AIDL services, verify caller identity and authorization on each request.
 Use signature permissions when applications share the appropriate signing identity. Different aggregator signers
require a deliberate partner trust model.
 Pass operation IDs and opaque references through IPC; avoid broadcasts and sensitive intent extras.
Android documents the risks of exposed components and the same-certificate behavior of signature permissions in
its component access-control guidance.
The SDK must represent pending and unknown results. After process death or connectivity loss, recover status using
the original operation ID. A UI cancellation does not prove that an authorization was cancelled.
Persist only the minimum recovery metadata. Do not use generic background retries to submit new authorizations.
Sensitive authentication data cannot be retained after authorization even when encrypted; this includes relevant
encrypted queues and diagnostic captures. See PCI storage guidance.
